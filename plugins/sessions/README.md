# sessions

A Claude Code mod (a plugin built on function hooks) that adds a side panel to every session with the sessions of the current project: what each one is doing, switching between them in a single terminal window, stopping, restarting and renaming them, grouping them in sections, and what you're spending. It also keeps background sessions with Remote Control alive while you drive them from your phone, tells you when a session has waited for you too long or spends far above its usual ([notifications](#notifications)), ships a status line, lets scripts hand a session a turn ([`ccc tell`](#telling-a-session-from-a-script)), lists and ends the sessions you no longer need ([`ccc tidy`](#ending-sessions)), lets Claude in one session list the project's others and wake a retired one ([tools for Claude](#waking-from-another-sessions-claude)), and gives other plugins an API to it ([`$.sessions`](#for-other-plugins)).

Tested on macOS (Terminal.app) with Claude Code 2.1.289 to 2.1.319. On Linux it switches windows through its launcher instead of driving the terminal app; that mode was tested on macOS, and on a real Linux desktop it still needs the short check in [`dev/sessions/linux-checklist.md`](../../dev/sessions/linux-checklist.md) (see [Linux](#linux)).

## Install

Requirements, on macOS and Linux: Claude Code 2.1.287 or newer (mods are on by default from there), `bash`, `python3` (on a Mac, the developer tools' one: `xcode-select --install`; `ccc`, the window's watcher, the panel's own file watch where `SessionStart` doesn't reach it, token usage and the setup run on it, and the setup stops without it), `jq` (status line), `git`. On macOS the window switching drives Terminal.app (not iTerm); the first time, macOS asks to let Claude control Terminal.

1. Add the marketplace and install the plugin (once per machine):
   ```sh
   claude plugin marketplace add mcavuoti/claude-plugins
   claude plugin install sessions@mcavuoti
   ```
2. Open Claude Code in any folder (`claude`). The panel shows up on the right in fullscreen windows 110 columns wide or more, and in a box above the prompt otherwise.
3. In that session, run the one-time setup for the pieces a plugin can't configure on its own:
   ```
   /sessions setup
   ```
   It sets the status line, the keyboard shortcuts (`shift+→` to the panel, `←` back to the prompt) and the `ccc` shell command, backing up every file it changes (`<file>.bak-antes-<what>-<date>`), and tells you which shell it detected. A `ccc` you already have, in your shell's startup file or a file it loads (`source`/`.`, such as `~/.bash_aliases`), is left as is: `already set` when it's this one. Add `--dry-run` to see what it would do first. Already have a status line? It's kept unless you add `--force-statusline`. On macOS, `--macos-launcher` also stops macOS from asking again for Desktop/Documents access after every Claude update (see [Background sessions on macOS](#background-sessions-on-macos)). You can also run it from a terminal: `bash ~/.claude/plugins/marketplaces/mcavuoti/plugins/sessions/setup/setup.sh --help`.
4. Open a new terminal (so `ccc` exists), go to a project folder and run `ccc`. It opens the folder's top session (the first row of its panel) right there, with the panel showing and holding the keyboard. In a folder with no sessions it asks for a name, starts the session and opens it. See [Opening sessions with ccc](#opening-sessions-with-ccc). Claude only starts background sessions in a folder you trusted: the first time in a folder, run `claude` there once (or `ccc --agents`) and accept its question.

Optional: turn on auto-update for this marketplace in `/plugin` → Marketplaces → `mcavuoti` → Enable auto-update. Otherwise, update with `claude plugin marketplace update mcavuoti && claude plugin update sessions@mcavuoti`.

Sessions that were already open pick the plugin up when they restart (`u` in the panel, or `claude respawn <id>`), or update themselves in place (below). An update that raises the shared format also needs `ccc` once more in each window opened with `ccc`: until then its launcher says the versions differ instead of switching, and leaves you at the shell. An update that only changes the launcher reaches a window already open when `ccc` runs in it again. The plugin keeps no code for older versions of itself: a session left on one (its row shows `↑`) may not do its share of the work the sessions split among them until it restarts.

**Updating in place.** When a newer version of the plugin is installed (after `claude plugin update`), each session's mod runs `/reload-plugins` in its own session, which loads the new version without restarting the session, and says "Panel updated to <version>". It does so only when it cuts nothing: the session idle (no turn running, no question or permission waiting, no background task), no New or Rename field open in its panel (it tries again later), and once per version. A panel that has the keyboard doesn't hold it back: after the reload it has the keyboard again, on the same row. What a reload covers: this plugin's code, and every other plugin's hooks, skills, agents and plugin MCP servers in that session, since `/reload-plugins` reloads them all (that's the tradeoff). What it doesn't: a newer Claude version, your settings and MCP servers of your own; for those, `u` restarts the session. A session whose update didn't take keeps its ↑ mark, and `u` is the way. Sessions on a folder copy of the plugin (development) never update this way. `ccc` always runs the installed version's launcher; the status line is a copy, so run `/sessions setup` again after an update that changes it.

**Coming from a folder install** (the mod loaded with `CLAUDE_CODE_PLUGIN_DIRS`): remove that variable from `env` in `~/.claude/settings.json` and disable the folder copy with `"enabledPlugins": {"sessions@inline": false}` in the same file. The second step matters because Claude's background service keeps the environment it started with and passes the old variable to every session it launches until it restarts.

## Opening sessions with ccc

| Command | Opens |
|---|---|
| `ccc` | The project's top session in this window: its most urgent one (waiting for you, then done and unseen, working, idle; sections don't change it), skipping stopped ones. If another window already shows a session of this project, that window comes to the front instead and nothing opens here. With no session to open, a Name prompt. |
| `ccc <name>` | The session with that name. If a window already shows it, that window comes to the front; if another window shows another session of the project, that window switches to it. A name that doesn't exist yet starts a new session with it. |
| `ccc --new` | This window, even if the project is open in another one: the top session not shown anywhere else (or the Name prompt if they all are). |
| `ccc --agents` | Claude's agent view for this folder. |
| `ccc tell <name\|id> "text"` | Hands that background session the text, as a turn of its own when it's idle (see [Telling a session from a script](#telling-a-session-from-a-script)). No window opens. |
| `ccc section <title>` | Puts the session this project's window shows in one of your sections, as `/sessions section` does inside it: `-` takes it out, no title says which one it's in, `--session <name\|id>` names another session of the project. No window opens. |
| `ccc tidy` | Lists every folder's sessions (`--here`: this project's) and ends the ones you pick: the stopped ones it removes, the idle background ones it stops and removes (below, and [Ending sessions](#ending-sessions)). No window opens. |

- **On arrival** the panel has the keyboard, on the row after the session you're in, as when you switch with Enter: Enter again hops on. A session waiting on a question or a permission keeps it: you land on the question.
- **The Name prompt** (an empty folder, or only stopped sessions) lists the stopped sessions with numbers: a number or a name reopens one, a new name starts a background session in the project folder and opens it once its panel is up (`Starting “name”…`). Enter on an empty line, or Ctrl+C, goes back to the shell; nothing is created until you type a name.
- **A session whose panel isn't running** (see [Old pre-started sessions](#old-pre-started-sessions)): `ccc` asks `Restart it first? [Y/n]` before opening it, Yes by default only when it's idle, since a restart cuts what it's doing. A session `ccc` itself just created and whose panel doesn't come up is restarted once without asking: it has no conversation to lose.
- **The project's window is brought forward** by a running session's panel (the platform code lives in the mod). Where that can't be done (Linux without `wmctrl` or `xdotool`, Wayland, a window Terminal.app doesn't have, or no session's panel answering), `ccc` says so and opens here, as `ccc --new` would.
- **Not trusted yet:** in a folder Claude never trusted, `claude --bg` refuses to start a session; `ccc` says so and how to trust it. In your home folder Claude doesn't start background sessions at all.
- **`ccc tidy`** lists the sessions of every folder from `claude agents --json --all` (`--here`: only this project's, by the same root as `ccc`, each session in the project it started in), in groups. Numbered, to pick: the stopped ones (no process: a list entry and its conversation on disk), oldest first, which it removes (`claude rm`); then the background ones running idle and not pinned, which it stops and removes (`claude stop`, then `claude rm`). Listed with why, and never offered: a session that's working or waiting for you (a question or a permission), one idle with tasks in the background (subagents, shells), one a window shows (a `claude attach` viewer or a `ccc` window), a pinned one (turn off Remote Control, or `--pinned` to offer it too; stopping a pinned one needs no unpin) and a regular one (`/exit` it in its window). Beside a stopped one, when it was last used: when its transcript was last written (`~/.claude/projects/*/<sessionId>.jsonl`, looked for by the session's id in every folder, since a folder's name can't be read back into a path and `/cd` moves the file to another one); without a transcript, when it started (`startedAt`, its first start, not its last run), saying so; and when it ended with Claude's background service (`ended with the background service at 14:05`: [When the background service goes down](#what-it-does)), so you see why it stopped. Beside a running one, how long it's been idle (`statusUpdatedAt` in Claude's registry of running sessions), or else when it started.
  - `Remove which?` takes numbers and ranges (`1 3-5`), `s` for every stopped one, and Enter for nothing. Running ones in the pick get a second question, `Stop and remove these 2 running sessions? [y/N]`, and each one is checked again just before it's stopped: one that turned busy or waiting, or that a window opened meanwhile, is skipped. A line per session says what happened: removed, stopped and removed, skipped (and why), or failed, with Claude's message (`claude rm` also deletes a worktree the session made, and refuses while that worktree has commits that aren't pushed; `ccc tidy` never passes the flags that force it).
  - `--days <n>` offers only the stopped sessions last used more than n days ago (without a transcript, started); `--list` prints the list and asks nothing. It reads the service's `pins.json` and job states and the transcripts' times, and never writes them. It exits 0 when it ran, picked or not, and 1 when the list couldn't be read or a stop or a remove failed.
- **What `ccc` hands its launcher stays there.** `ccc` tells the launcher the installed version and since when (`SESSIONS_PLUGIN_VERSION`, `SESSIONS_PLUGIN_SINCE`). No `claude` the launcher or the mod runs gets them, so they never reach Claude's background service or the sessions it starts.

## Telling a session from a script

`ccc tell <name|id> "text"` (or `-` to read the text from stdin) lets any script hand a background session some text: a cron job, a launchd or systemd timer, a git hook, a mail watcher. That session's mod submits it as a turn of its own once the session is idle; the model reads it as a message from the sessions plugin, marked as sent by a script, never as yours. It needs no terminal and no project folder: the session is found by its id, by its name in the current folder's project (`--in <folder>` names another), or by a name only one background session has (an ambiguous name is refused with the matches).

- **Opt-in, per session:** `/sessions tell on` in that session (`/sessions tell off` turns it off; `/sessions tell` says which). Without it every request is refused. A regular session (plain `claude`, with you at it) can't opt in.
- **4 KB at most.** Send pointers, not outside text: "new mail, id 4412: read it with the mail tool" rather than the mail itself. What a script passes on is untrusted (anyone can mail you), and the session should fetch it with its own tools, where its usual checks apply.
- **A status file** for every request, `~/.claude/mods/sessions-data/tell/<id>/<request>.status`, with `state=`: `queued` (waiting for the session to be idle), `delivered` (its turn started), `held` (you stopped the session with Esc, and Claude refuses plugin prompts until you type in it: it goes once you do), or `refused` with `reason=`. `ccc tell` prints the state it sees within 2 s and the file's path, and exits 1 when refused. A request the session took but whose turn never came (it restarted, or was retired, first) goes back in line, `queued` again; one whose submit failed is tried once more, then refused.
- **`--wait`** (or `--wait=<seconds>`, 300 by default) waits for the outcome instead: it prints the final state and exits 0 when delivered, 1 when refused, 3 when held, and 4 when the time ran out with the request still queued (it stays queued). A stopped session it wakes counts its wake in the wait.
- **At most 6 requests a minute, and 60 an hour,** reach one session: the rest are refused, saying when to try again, so a script gone wrong can't flood it.
- **A stopped session** that Claude's background service retired for being idle, or that ended by itself (a crash, or the machine or the service restarting under it), is woken first (`claude respawn`, asked of a session whose panel runs, under the same rules as `$.sessions.wake`); one you stopped (`claude stop`, or `s` in the panel), one with nothing in the service's log to say why it stopped, or closed for lack of memory while memory is still short, is refused (a plugin acting on a command of yours can ask `$.sessions.wake` to wake the ones you stopped: `docs/plugin-contract.md`). A session whose panel isn't running is refused too (`u` restarts it).
- `ccc tell` itself runs the enabled plugin's launcher like `ccc` does, so the job's `PATH` needs `claude` and `python3` (cron and launchd give a short one: set `PATH`, or `SESSIONS_CLAUDE` to claude's full path). A session named `tell`, `section` or `tidy` can't be opened with `ccc tell`, `ccc section` or `ccc tidy`: use `ccc` and its Name prompt, or its id.

## Ending sessions

A session ends only when something ends it, so the ones you're done with stay until you end them.

- **What keeps one alive.** A regular session (`claude`) runs until you `/exit` it in its window. A background one runs with no window attached until Claude's background service retires it: after an hour idle with no window attached and nothing running in the background, or 8 hours with Remote Control. A pinned one (◆: the mod pins each one with Remote Control on) isn't retired for being idle at all, only when memory runs short ([Reopening after a memory shortage](#what-it-does)).
- **Stopped** means no process: the session stays in the list (gray) with its conversation, and opening it (`ccc <name>`, Enter in a panel, `claude attach <id>`) starts it again. **Removed** means gone from the list too (`claude rm`, which also deletes a worktree the session made): its conversation file stays in `~/.claude/projects/`, but no panel, `ccc` or agent view lists it.
- **To end one**, `s` on its row in a panel → Stop & Remove (Remove from list for a stopped one). For many at once, [`ccc tidy`](#opening-sessions-with-ccc).
- **Retired isn't ended.** A background session the service retired for being idle, or that ended by itself (a crash, a restart of the machine or the service), can come back without you: `ccc tell` and other plugins wake it, and so does Claude in another session of the project ([below](#waking-from-another-sessions-claude)). One you stopped stays stopped until you start it.
- **Don't kill claude processes by hand** (`kill`, Activity Monitor): a killed session looks like one that crashed, not one you stopped. It stays in the list, and since nothing says you stopped it, `ccc tell`, other plugins and Claude in another session may wake it again (they wake a session that ended by itself, never one you stopped).

## Waking from another session's Claude

Claude in each session can list the project's other sessions and bring back a stopped one, so it can talk to it with Claude's own SendMessage. Say a "lead" session coordinates two background workers: after an hour idle the service retires the workers, and a message to a stopped session fails at once (it isn't kept for it). The lead's Claude then wakes them first. It's generic: it works for any sessions of a project, whatever made them.

- **Two tools**, `mcp__sessions__list` and `mcp__sessions__wake`, behind ToolSearch (deferred: they cost nothing until Claude looks for them). The list gives, for each other session of the project, Claude's name for it (what ListAgents and SendMessage use), its short id, whether it's working, idle, waiting for you or stopped and why (retired for being idle, ended by itself, closed for lack of memory, stopped by you, or nothing says), whether it can be woken (and why not), and the agent it runs as. `mcp__sessions__wake` takes a name or short id, restarts the session with its conversation (`claude respawn`, as `$.sessions.wake` does), waits until it runs (about a second) and answers the name to SendMessage to, `"worker [ab12cd]"` (the part in brackets changes at each restart). The wake itself starts no turn there and spends nothing: only the message Claude sends next does.
- **What it wakes**: a background session of this project, other than the one asking, that the service retired for being idle or that ended by itself, or one closed for lack of memory once memory is normal again. Never one you stopped (`s` in a panel, or `claude stop`), one with nothing in the service's log to say why it stopped, a regular session, or one of another project; nothing at all while memory is short. Only the main conversation can wake (not a subagent or a teammate), at most 6 sessions in 10 minutes and 20 an hour per asking session, and the same session at most 3 times an hour (one that fails to start isn't woken in a loop); the refusal says when it can try again. Two sessions, or a session and a panel's `b`, never restart the same one twice, and one started meanwhile (Enter in a panel) is found running instead.
- **You see it**: the woken session's row says `woken by “lead”` under it, in every panel, for 15 minutes; the asking session shows a toast; and with debug logs on, its debug log has a line for each wake and each refusal.
- **Permissions**: the tools never put a question to you, since the mod answers them itself. A `deny` rule for one (`"mcp__sessions__wake"` in `permissions.deny`) takes it away; an `ask` rule makes it refuse, saying so, in place of the question it can't ask.
- **In an agent** (`claude --agent <name>`): an agent sees only the tools its `tools:` line names. A lead that runs as one needs `mcp__sessions__*` (or both names) and `SendMessage` in its agent file's `tools:` (no `tools:` line gives it every tool). The mod reads the agent file (`<folder>/.claude/agents/<name>.md`, for the folder the session started in and those above it, then `~/.claude/agents/<name>.md`) and doesn't offer the tools to an agent that leaves them out: offering one anyway holds that session's every start and restart 8 s. An agent with no file there (a plugin's, or `--agents`) gets them with a short wait (0.3 s at most).
- **Where `SessionStart` never reaches the mod** (a plugin ahead of it keeps it: see [When SessionStart doesn't reach sessions](#when-sessionstart-doesnt-reach-sessions)): the agent comes from Claude's registry or the background job's flags at the start, and the tools are offered as usual. Where neither says in half a second, they're offered as for no agent without holding the start: a plain session sees them from its next request.
- **Off**: the option **Tools for Claude to list and wake this project's sessions** (`sessionTools`, on by default) turns both off. `/sessions status` says which tools this session has, or why not.

## What it does

- **Session list** for the project folder and its subfolders. The project is the nearest folder upwards with an `AGENTS.md` or `CLAUDE.md`, or else the session's folder. A worktree under `<project>/.claude/worktrees/` (EnterWorktree, or a background session that isolated itself) is that project, with every session of it, even when the worktree has its own copy of `CLAUDE.md`. A session opened in your home folder (~) lists only that folder, not everything under it. A session stays in the project it started in, wherever it goes afterwards (a worktree inside or outside the project, of its repository or another one, a folder `/cd` took it to): it's listed there in every panel of the project, its own included, and in `ccc`, never in the folder it moved to ([which project a session belongs to](#how-it-works)). Its own panel then says where it works, under the legend: `Working in ~/x/wt, outside this project`. Each row has a colored dot, the name, the model, the share of the context window used and how long ago:
  - red: waiting for you (a permission, a question);
  - blue: working;
  - yellow: finished and you haven't looked yet (it turns green when you type in it, use its panel, arrive there from another session's panel (Enter or a click on its row) or with `ccc`, or the panel sees its window in front);
  - green: idle and seen;
  - gray: stopped.
- **Sections**: `/sessions section <title>` in a session puts it in a section of yours (made the first time; `Renders` and `renders` are the same one), `/sessions section -` takes it out (a section of yours with nobody left in it goes), `/sessions section` says which one it's in and `/sessions sections` lists them all. From a shell in the project folder, `ccc section <title>` does the same for the session the project's window shows. Other plugins can make sections of their own (`<plugin>:<name>`) and put sessions in them, but never move one you placed. The panel shows the sessions in no section first, then each section under its title (dim, and the arrows skip it), only when two or more groups have rows: a project that uses no sections looks as it always did. Sections are kept in `~/.claude/mods/sessions-data/sections.json` and apply to the session in every project; a session that's gone from the list leaves its section, and a plugin's section that stays empty for 10 to 20 minutes goes too (the plugin makes it again when it needs it).
- **Marks from other plugins**: a short badge after a session's name (`?2`) and a status line under it ("doing X / blocked on Y"), which another plugin sets and refreshes; they go by themselves within 10 minutes once it stops. `/sessions status` says whose they are.
- **Under their parent**: another plugin can put a session under another one (a helper under the session it works for): it's drawn right under it, two columns in, in the parent's section, while the parent is in the list. While the parent waits for you (red, or marked as needing you) in another section than the helper's own (one its plugin moved it to while it asks you, say), the helper stays in its own section: it isn't the one waiting.
- **Folding a section** (`c`): `c` on a session folds its section into one line, `▸ Renders · 4 · 1 waiting for you`; Enter (or `c`) on that line unfolds it; the other rows stay where they are (a pending sort waits until you leave the panel). Only sections with a title fold, and nothing folds while `f` shows only who's waiting. Which sections are folded is remembered for every session.
- **Nothing moves while you're in the panel**: new sessions go at the end, and sorting, a session's new section or parent, folds made in another session and the filter below apply when you leave it (Claude follows the focus by position, so a row moving under it would put the highlight on another session).
- **Waiting for you** (`f`): only the sessions waiting for you (red, or marked by another plugin as needing you), with a line above them, `Waiting for you · 3 of 17`; `f` again shows them all. It's remembered for every session, so you can hop through them with Enter. Who's in the list is taken when you turn it on and whenever you're not in the panel: one you answered stays, in its new color, until you leave; `f` twice takes it again without leaving.
- **Spend**, read from each session (never assumed): on a subscription, the line above the prompt shows each of the account's windows that it reports, once (`7d 43%`; the 5-hour one too when there's one); on an API account (no windows), each row shows what its session has cost so far, as `/cost` says, and a line under the legend the project's total, `$4.80 est. spent here so far (list price)`. A session that hasn't answered yet shows neither.
- **⚙n after a name**: that background session has n things running in the background beside its turn (subagents, background shells), as Claude's background service counts them: a session that looks idle may still be working.
- **⧗ before the time**: that session has been working for an hour or more (`⧗2h`: maybe a loop), or it's a background session whose answer has waited unseen that long. Dim, in the time's column: nothing moves for it. The hour is an option ([Notifications](#notifications)).
- **A warning line under a row**, `$6.00 in the last hour · usually $0.50` (on a subscription, `spending 12× its usual hour · 7d +3% this hour`): that session spends far above its own usual hour (see [Notifications](#notifications)). Nothing is stopped.
- **The session you're in** is highlighted with a bar on the left. You can select it with the arrows like the others (even when it's the only one), to restart or rename it; Enter there does nothing, and `s` won't stop it (that would leave you without a window).
- **Switching sessions in the same window**: Enter on a row, or a click on it. The window keeps showing the session you left until the other one draws over it, about a seventh of a second later: no blank screen, no shell in between. A key you press meanwhile isn't printed over it and is dropped: it never lands in the other session's prompt box, where a second Enter would send what that box holds. On arrival with Enter, the other session's panel already has the keyboard, so you can hop through several with Enter; by a click, the keyboard stays where it was in that session. If the other session is already open in another window, that window comes to the front. Windows switch in place when they were opened with `ccc` (or by the panel); from a window opened another way (`claude attach` typed by hand), Enter opens the session in a new window next to it. A regular session (plain `claude`, not a background one) lives in its own window: Enter brings that window up, and if it runs somewhere the panel can't reach (tmux, another app), it tells you.
- **`!` after a name**: that session's panel isn't running (its mod never started, or it runs another version of the mod). Nothing is sent to it, questions about it are asked here, and `u` restarts it.
- **Stop** (`s`): Stop, Stop & Remove, or Cancel. The question shows up in the session you're stopping: the window goes there, you answer, and it comes back. A session that can't show a dialog (its agent leaves AskUserQuestion out of its tools) sends the window back, and the question is asked in yours; so is it when your own session can't send notices (no SendMessage in its tools). Afterwards a Terminal window that showed only that session closes; one with other tabs stays as it is (its tab is back at its shell).
- **Restart** (`u`): restarts the selected session, yours included: a new process with the same conversation and name, which reloads MCP servers, plugins and settings (say, after adding an MCP server) and moves to the installed Claude version. Sessions on an older Claude version, or an older version of this plugin, are marked ↑. It always asks first: if the other session is working, waiting for you or has background tasks, the question shows up there; if it's idle, here. Restarting your own session, the window comes back to it by itself and says "Restarted". Background sessions only: restart a regular one with `/exit` and `claude -c`.
- **Rename** (`r`): opens a field under the list for the selected session's new name (yours, if it's the only one). The session renames itself with the official `/rename`, so the name changes in `claude agents` and on your phone too; if it's busy, it does so when it finishes. A session started with plain `claude` gets an automatic name (folder + two characters, like `myapp-1f`): rename it with `r` from another panel or `/rename <name>` inside it, and the panels pick it up within a second. You can also start with a name: `claude -n "name"`.
- **Pinning with Remote Control** (◆): Claude's background service closes an idle session with no window attached after an hour, or after 8 hours if it has Remote Control. A pinned session (Ctrl+T in `claude agents`) isn't closed. The mod pins every background session you turn Remote Control on for, in any folder, within about a second (a minute at most), and unpins it when you turn it off. It only unpins the ones it pinned: yours stay. If you unpin one it pinned, it won't pin it again until Remote Control goes off and on again.
- **Reopening after a memory shortage**: when the machine runs out of memory (critical memory pressure on macOS, less than 1 GB free on Linux), the background service closes idle sessions, pinned ones too. The mod reopens the pinned ones with Remote Control that were closed for that reason once memory has been back to normal for 3 minutes in a row: same conversation, same Remote Control address, one at a time, at most 3 times in 2 hours each. One you stopped yourself isn't reopened. It needs at least one other live session running the mod.
- **When the background service goes down** (the machine restarted, or the service crashed or was killed), every background session it ran stops with it, and they stay stopped (gray) until you open each one. Every panel then says so under its legend, counting every folder's: `3 sessions ended with the background service at 14:05 · b: brings them back`. `b` asks first, saying how many and from which folders, then restarts them one at a time, a few seconds apart, each with its conversation (`claude respawn`), and looks at each one again just before: one that runs again, or that you stopped or removed meanwhile, is skipped. It never restarts a session you stopped yourself, one the service retired for being idle, or one that crashed. A toast says how it went (`Brought back 3 sessions, skipped 0, failed 0`). `Leave them stopped`, in the same question, hides the line until the service ends sessions again. In [`ccc tidy`](#opening-sessions-with-ccc) they're marked too.
- **New** (`n`): asks for a name, creates a background session and switches to it. A name another session of the project already has isn't taken (`ccc <name>` could then open either): the field stays open for another. Enter without a name gives it one after the folder, like the names Claude gives regular sessions (`myapp-1f`), unused by the project's other sessions. (In `ccc`'s Name prompt, Enter on an empty line still goes back to the shell.)
- **The New and Rename fields** keep you in them until you're done: Enter does it (an empty Rename field cancels), Esc cancels, and the arrows and Tab don't take you out, so a half-typed field can't be left behind.
- **Agents** (`a`): opens Claude's agent view (`claude agents`) in the same window. The agent view draws no panels (they show only in a session's own screen): open a session from it, or `←` back from one, to see the panel again.
- **Token usage**, at the bottom: bars for today by hour (`d`), 7 days (`w`) or 30 days (`m`), for all of Claude on this machine or just this project (`p`).
- **Status line** (after `/sessions setup`): model · effort · folder · git branch · context % · cost.
- **Closing the panel**: close it yourself (its ✕ or close key, or `/sessions` while it has the keyboard) and it stays closed, in this session and in every session that starts afterwards, until you open it again with `/sessions` or the button on the line above the prompt (`shift+→` then Enter, or a click). What you chose wins: arriving with `ccc` or Enter then lands on the prompt instead of the panel.
- **More sessions than the panel's height**: a line at the top says how many don't fit (`↓ 4 more below`, and the keys that scroll), and while the list doesn't fit, only the rows that wait for you, or that a plugin marked as needing you, keep their status lines (their badges stay), so more sessions fit.
- **Live: what changed shows within a second, with nothing asked.** Another session turning busy, done or waiting for you, starting, ending or renamed shows in about 0.6 s (one that ends, in about 0.2 s), and your own row at once: Claude tells each panel when one of a few files changes ([Watching files](#how-it-works)). An idle panel runs no command, is drawn about once a minute (for a row's time) and reads everything again once a minute in case an event was missed; one session does the machine-wide work for all of them ([The leader](#how-it-works)).
- **Updated in place, it says so.** A version that watches other files than the running one is never loaded in place: the `↑` stays and `u` restarts. A session that came in by a `/reload-plugins` you ran yourself across such a version, or one a plugin ahead of sessions keeps `SessionStart` from, watches the files itself and stays live ([When SessionStart doesn't reach sessions](#when-sessionstart-doesnt-reach-sessions)); while that watch is down, the first says `Live updates off: this session was updated in place; u restarts it, or /clear` and reads the files every 3 s until it restarts, is cleared or compacts, and the second reads them every 3 s and says nothing about `u`, which wouldn't help.
- Above each session's prompt, one line (and after it whatever other mods draw there): how many sessions are waiting for you (red) or have something unseen (yellow), the account's windows on a subscription, and when the panel isn't shown, why: `panel closed · /sessions to open`, or `panel hidden: window too narrow · /sessions to show` (Claude draws a panel the mod opened on its own only from 144 columns, 110 once you've opened it yourself; one you open with `/sessions` shows at any width).

## Notifications

The panel tells you, at most once each, when a session of the project has waited for you too long, and when a session spends far above its usual hour. It never stops anything, and it costs no tokens.

- **Waiting too long**: once a session has waited for you (red: a question or a permission, or marked by another plugin as needing you) for 10 minutes, you're told once for that wait, with the sessions' names only: `“Release notes” has been waiting for you for 10 min`. When several are due at once, one notification names the first and counts the others. The next wait of the same session counts again.
- **Spending far above its usual hour**: each session measures what it spends an hour (its cost at list price, as `/cost` says; on a subscription that's a measure of its tokens, not a bill) against its own usual hour, the median of its active hours over the last day. Four times that and $3 or more marks its row (above) and tells you once, until it falls below half of both: `“Data pipeline” spent $6.00 in the last hour, usually $0.50: check it isn't looping`. It needs an hour of history to judge; until a session has three active hours of its own, its usual hour is its project's (the median of what the project's other sessions usually spend an hour), so one that loops from its first hour is told too (`$20.00 last hour · project's usual $0.50`).
- **How it reaches you**: first Claude's PushNotification, which goes to your phone when the session sending it has Remote Control and you're away from the computer (Claude doesn't send it while you're at it); otherwise a notification through your own channel (your `preferredNotifChannel` setting, and your `Notification` hooks), which depends on the terminal: Claude's channels are iTerm2, kitty, Ghostty and the terminal bell (a bell, no text); in another terminal, such as Terminal.app, only your `Notification` hooks get it. Whichever session of the project gets there first sends it, a session with Remote Control a minute before the others, so it comes once and from one that can reach the phone. `/sessions status` says what the last one said and what each channel answered.
- **Options** (`/config`, or `"pluginConfigs": {"sessions@mcavuoti": {"options": {…}}}` in `~/.claude/settings.json`):

| Option | Default | Does |
|---|---|---|
| `waitPushMinutes` | 10 | minutes a session waits for you before you're told (0: never) |
| `quietHours` | none | no notifications in these local hours, written as `22-7` or `22:30-07:00` |
| `notificationsPerDay` | 5 | the most notifications a day, of both kinds together (0: none) |
| `staleMinutes` | 60 | minutes before the ⧗ (0: never) |
| `sessionTools` | on | Claude's tools to list and wake this project's sessions ([Waking from another session's Claude](#waking-from-another-sessions-claude)) |

`/sessions` opens the panel with the keyboard (or closes it, if it has it). `/sessions section <title>`, `/sessions section -` and `/sessions sections` put this session in a section, take it out, and list them (see Sections above). `/sessions tell on` (`off`) lets scripts hand this session text with `ccc tell`. `/sessions status` says whether the mod runs in this session and what started it, whether it's live (watched files) or on the short timer and why (an update in place, which `u` or `/clear` ends, or a plugin ahead of sessions that keeps `SessionStart` from it, which nothing here ends), where its list comes from and which session leads (`session.start`, or the first draw, prompt or notice when that never came), the session's id and project folder, the mod's version and whether it's the installed copy or a folder copy, when it last wrote its heartbeat, which sessions of the project have no running panel, the API it serves other plugins, the tools it gave Claude here (or why none, and where the agent came from when `SessionStart` didn't say it), its sections, the notifications sent today and the last one, and this session's spend against its usual hour.

A plain `→` can't go to the panel only when the prompt is empty, the way `←` goes to the agent view: that `←` is built into the prompt box, and Claude's key bindings can't be conditioned on an empty prompt. Hence `shift+→`.

## For other plugins

The mod adds `$.sessions` to the API other mods see (api 1): what this session is (its short id, name, project root, the agent it runs as), the state of other sessions by short id or name, sections of their own in the panel with sessions under a parent, starting a session (`--agent`, `--settings`), waking one retired for being idle or ended by a crash or a restart (and why each stopped one is stopped), marks on rows (a badge, a status line, "needs you"), pinning a background session so the service doesn't retire it (only the pins a plugin added are ever unpinned, never yours), restarting an idle one from the mod's own timer, and the command for a file watch of the plugin's own (the mod's own watcher, below, which the plugin runs and reads itself). It spends no tokens (the mod's only turns are [`ccc tell`](#telling-a-session-from-a-script)'s, in a background session you opted in). A plugin can also refuse a wake that Claude asks for with [`mcp__sessions__wake`](#waking-from-another-sessions-claude), whose input stays as it is (the docs say how). A plugin lists `sessions` under `dependencies` in its `plugin.json`, calls only (it never hooks `sessions.*` events or reads the mod's files), and checks what's served with `contract()` first. How to call it and how it changes: [`docs/plugin-contract.md`](docs/plugin-contract.md); the types: [`types/index.d.ts`](types/index.d.ts).

## Debug logs

Off by default. Turn on **Debug logs for new sessions** in the plugin's options (`/config`, or `"pluginConfigs": {"sessions@mcavuoti": {"options": {"debugLogs": true}}}` in `~/.claude/settings.json`). Then every session the panel (`n`) or `ccc` creates starts with `--debug-file ~/.claude/mods/sessions-data/debug/<name>.log` (Claude's own debug log, which works with background sessions), and the mod writes a line there for each step of its start. Restarting such a session (`u`, `claude respawn`) keeps writing to the same file. Sessions created before you turned it on, or another way, don't log. The mod mirrors the option to `~/.claude/mods/sessions-data/config` for `ccc`, which can't read plugin options.

## When SessionStart doesn't reach sessions

On some installs of Claude, such as one an organisation manages (on macOS or Linux), a plugin runs before the plugins you installed, takes Claude's `SessionStart` and sends it on past them: one the organisation manages, or one built into that Claude. Claude then says at every start `sessions: its classic.SessionStart hook was skipped. "<plugin>" runs first and sent the event on past it.` A restart (`u`) doesn't change that, and the mod can't name that plugin itself: Claude tells a plugin nothing about who skipped it (the line at the start names it).

`SessionStart` is where the mod learns two things, and it has a stand-in for each:

- **The agent the session runs as**, which decides the tools for Claude: the mod reads it from Claude's registry of running sessions (`~/.claude/sessions/<pid>.json`, whose `agent` names it from the session's start) or, for a background session, its job's flags (`--agent <name>` in `~/.claude/jobs/<id>/state.json`), and offers the tools as it would after `SessionStart` (an agent whose `tools:` line leaves them out gets none). If neither says within half a second, it offers them as for no agent without holding the start: a plain session sees them from its next request, and an agent session never does, which holds nothing either.
- **What Claude watches for the panel**: Claude watches files for a mod only for what its `SessionStart` hands back (`watchPaths`), and a mod has no other way to ask. So the mod watches them itself: one process per session (`hooks/watcher.py watch-paths`, with the kernel's file watch: kqueue on macOS, inotify on Linux) over the same paths, which sleeps until one of them changes and then tells the mod at once, as Claude's event would. Once it's up the session is live, as one Claude watches for: another session's change shows within a tenth of a second, and nothing runs every few seconds. It starts as soon as it's clear no `SessionStart` is coming (at once on a machine whose starts are known to get none, or in a session updated in place; else 10 s after the start), ends with the session, and ends when a `SessionStart` does come (a `/clear` or compaction on a machine that sends it: Claude watches from then on); a reload ends it with the module, and the new module starts its own. It ends by itself when the session's process does, even killed outright, and when the mod stops reading it, so it never outlives the session. Another plugin can run the same watcher over its own paths (`$.sessions.watchCommand`, in [`docs/plugin-contract.md`](docs/plugin-contract.md)). Until it says it's ready, and for the 30 s after it ends before it starts again (5 times in a row at most), the panel reads the files every 3 s, as before. It needs `python3` (a requirement: see [Install](#install)).

The first start on such a machine waits up to a second for a `SessionStart` that doesn't come; after it the machine remembers (the store's `startSkipped`), and later starts don't wait for one, until a `SessionStart` reaches the mod again. Everything else works as usual. `/sessions status` says so: `Live through the mod's own watch (no SessionStart came: a plugin that runs before sessions sends it on past it): kqueue on 6 paths (14 watched), process 4321, since 80 s ago`; while it's down, `Not live: no SessionStart reached the mod in this session: a plugin that runs before sessions (such as a managed or built-in one) sent it on past it…; its own watch ended (…) and starts again in 30 s`; with no usable `python3`, a `Problem:` line says to install it. Its `Tools for Claude` line says where the agent came from (`from Claude's registry of sessions, since no SessionStart reached the mod`).

## Linux

On macOS the panel drives Terminal.app (which window is in front, bring one forward, open one). On Linux there's no portable way to drive a terminal, so the panel works from processes and its launcher only, which every terminal has, and asks the X11 desktop which window is in front:

- **The window you're in** is the one whose launcher has your session open (what its launcher publishes, else found with `ps`). Open your windows with `ccc` (or the panel's Enter, New and Agents, which use the launcher too). `ccc` brings the project's window forward the same way the panel does (`wmctrl`/`xdotool`), or opens here when it can't.
- **Switching** happens in that same window, through the launcher, exactly as on macOS.
- **A session already open in another window** is brought forward with `wmctrl` or `xdotool` when one is installed (X11; the launcher titles each window with its session's name, and the whole title is matched, so no other window whose title holds that name comes up). On Wayland, or without either tool, the session opens in the current window too.
- **Seen** (yellow → green): on X11 with `xprop` (part of the X11 utilities on most desktops), the panel reads the title of the window in front: a viewer titles its window with Claude's status mark and the session's name (`✳ name`, which a terminal may put inside its own words, `Terminal - ✳ name` or `✳ name – Konsole`), and a session whose whole name it shows is seen. A session with no name of its own, or a name another session also has, isn't told apart this way, nor is one inside an agent view. On Wayland, or without `xprop`, it stays yellow until you type in that session, use its panel or arrive there (Enter or a click in another panel, or `ccc`). There's no telling whether you're at the computer, so a window left in front while you're away counts as seen.
- **A new window** (for example, pressing Enter in the panel of a regular `claude` session, which can't be switched in place) opens with `$TERMINAL` if it's a known one, else `x-terminal-emulator`, GNOME Terminal (`gnome-terminal`, `kgx`, `ptyxis`), Konsole, Xfce Terminal, kitty, Alacritty, WezTerm, foot, Tilix, Terminator or xterm, whichever is found first.

| Feature | On Linux |
|---|---|
| List with colors, model, context % and time | works |
| Enter to switch, New, Agents (`a`) | works in windows that run the launcher (`ccc`) |
| Stop, Stop & Remove, Restart, Rename | works; questions show up in the other session, as on macOS |
| Bring forward a window showing another session | X11 with `wmctrl` or `xdotool`; otherwise it opens in the current window |
| A window opened without the launcher (`claude attach` typed by hand) | can't be switched in place (there's no way to type into it): open it with `ccc` |
| ↑ for an outdated version, token usage, pinning (◆), reopening after a memory shortage | works (version and folders read from `/proc`, memory from `/proc/meminfo`) |
| Live updates where `SessionStart` doesn't reach sessions | the mod's own watch with inotify: one instance per session (`fs.inotify.max_user_instances`, 128 on many systems); past that limit a session reads on the short timer, and `/sessions status` says why |
| Automatic "seen" (yellow → green) | X11 with `xprop`: the window in front, by its title (a session with a name of its own, not inside an agent view); otherwise it stays yellow until you type in that session, use its panel or arrive there |
| Closing the windows of a stopped session | not needed: the viewer ends with the session and the launcher leaves the shell |

**Older distributions** (tried on CentOS 7): where the system's glibc is too old for Claude's binary and Claude runs through the glibc loader (`ld-linux… --library-path … …/claude/versions/X.Y.Z`), `ps` lists its viewers and agent views as the loader's command line; the mod and the launcher read such a line as `claude <args>`, and take the program from `/proc/<pid>/cmdline`. The `ps` calls pass one `-o` per column, since an older procps reads `-o pid=,tty=,command=` as the pid column alone.

To try this mode on a Mac, start test sessions with `SESSIONS_PORTABLE=1` in their `--settings` `env`.

## Background sessions on macOS

macOS stores a program's permission for protected folders (Desktop, Documents, Downloads) by its path and signature, and each Claude version installs to a new path. Background sessions then ask for that permission again after every update, and one relaunched while nobody is at the Mac dies waiting for the prompt. `/sessions setup --macos-launcher` installs `extras/macos/claude-bg-launcher` as Claude's process launcher (`CLAUDE_CODE_PROCESS_WRAPPER`): it runs background sessions from a copy of Claude at a fixed path, so the permission is granted once. It only changes which file is run, following Claude's launcher contract.

## How it works

**Session data.** Claude's own files and official sources: the registry of running sessions (`~/.claude/sessions/<pid>.json`; `/^\d+\.json$/` only, the `.key` beside each is no session; status `shell`, a turn that ended with a background command still running, counts as busy, as `claude agents` does; a pre-started spare and a parked job are left out) and the background service's stopped jobs (`~/.claude/jobs/<id>/state.json`), which together give what `claude agents --json --all` lists (its `status`, not `state`, which is an AI summary and gets things wrong); that listing itself once a minute by the leader, and by every session when the files can't be read; `claude plugin list --json`, the mod's events (`turn.start`, `turn.complete`, `session.receive`, `prompt.submit`) and `$.store`, the shared store Claude manages. Each session records its model, context %, version and when it finished there, and what it spends (its cost and the account's rate-limit windows, from `$.session.usage()`, the status line's figures), its project root and the agent it runs as. The agent comes from its transcript (`~/.claude/projects/<folder>/<id>.jsonl`): Claude writes an `agent-setting` row when a session started with `--agent` starts or restarts; after `/clear` the new conversation has none and the mod keeps the one it knew. Without the files, the official list is shared through the store and read again only when Claude's registry of running sessions or the service's job folders moved, or 30 s passed (3.5 s with no registry to go by), one session at a time (`list.lock`).

**Starting in a session.** The mod starts once per session, from whichever comes first: `session.start`, the first draw of the line above the prompt (a background session draws even with no window attached, and a draw's own `$` can start timers, open the panel and register `/sessions`, though it can't write the panel's values until that draw has settled, so the start's first write waits for it), a prompt you type, or a notice from another session. The steps go one by one, each able to fail alone: the session's id and folders, its record, its heartbeat, the timers, the panel, and `/sessions` last. `/clear` (and `/resume`) keep the process but give the session a new id (the short id `claude attach` takes stays) and raise no new `session.start`: the mod follows the new id (on the `SessionStart` that comes with it, on `session.end`, and on its pass in case nothing announced it), moving the session's record, heartbeat and inbox over, and a regular session's section (named by its session id; a background one is named by its short id, which stays); the old conversation's title and finish time don't carry over.

**Which project a session belongs to.** The one it started in (`sessionHome` in `hooks/state.ts`, which `hooks/launcher.py` and `hooks/usage.py` follow too). Claude lists a session where it is now: EnterWorktree with a path, ExitWorktree and `/cd` move its registry file and its row in `claude agents`, so that folder alone took a session out of its project's panels and put its own panel on the other folder. In order, from the best source there is:
- what its own mod recorded at its first start: the project of the folder it started in (its transcript's first row when it has one already, else `$.session.root()`), kept in the store (`project:<sessionId>`) across restarts (`claude respawn` keeps the session id, and starts it again where it was) and carried over to the new id by `/clear` and `/resume`, and published as `root=` in its heartbeat (an addition to the format: older readers ignore it);
- for a session whose mod doesn't run (stopped, for one): where its transcript started, the `cwd` of its first row that has one (the rows after a move carry the new folder, and the file moves to the new folder's `~/.claude/projects/` folder, but the first row stays), found by the session's id in every folder, once per session (one `grep` for all the new ones; one with no transcript is looked for again only once it runs);
- the folder Claude lists it in.
A heartbeat's root is kept once read (it never changes for a session id), so a refresh runs no command for it.

**Heartbeats.** Each session's mod rewrites `~/.claude/mods/sessions-data/alive/<sessionId>` every 15 s (its process id, the time, the mod's version, what started it, the project it belongs to). A session that runs, started more than 30 s ago and after the installed version was installed (`claude plugin list --json`), but has no fresh heartbeat from its current process, has a mod that never started: its row gets `!`, and `ccc` offers to restart it. A session started before that version was installed isn't flagged: it runs an older mod, which isn't broken. The heartbeat is also how a session is known to be able to lead (below): a mod can't ask whether another process is alive without running a command.

**Watching files.** At `SessionStart` (a start, `/clear`, a compaction, a resume) the mod hands Claude the paths to watch for the session (`watchPaths`, added to the ones the plugins beneath ask for; `hooks/watch.ts`; where no `SessionStart` reaches the mod, its own watch takes the same paths: [When SessionStart doesn't reach sessions](#when-sessionstart-doesnt-reach-sessions)): Claude's registry of running sessions (`~/.claude/sessions`, read only), `bell/`, `inbox/` and `tell/` in the data folder (made first where missing: Claude may never watch a folder that's missing when it's asked for), the background service's `pins.json` and, in a background session, its own `~/.claude/jobs/<id>/state.json`. Never the whole `~/.claude/jobs` (Claude watches a folder to every depth, and that one holds hundreds of folders), nor the store's file (reading it touches it). Claude raises `classic.FileChanged` about 0.6 s after a file changes or appears (it waits for the size to hold for 0.5 s, so a burst of writes is one event) and about 0.15 s after one goes, in a background session with no viewer too. The mod notes what kind of file it was and, 30 ms later, reads only that: the registry files that moved (by time and size), the store records a bell names, `ccc`'s requests. The registry and the service's stopped jobs give the list `claude agents --json --all` prints (`directList`; `dev/sessions/ui-bench/equivalence.py` compares the two on a real machine); a registry file it can't parse twice, or this session missing from it, puts that session back on `claude agents`, every 3.5 s at most, and the panel says "List read the slow way". What sessions keep in the store for each other (each one's record, seen and title, the marks, the shared `f` and `c`, an answer to a Stop or Restart question) comes with a bell, and so do `sections.json`, the pins and the token usage summary: the writer rewrites `bell/<what>` (who rang it and when, never the data), and the readers read that again; until then they keep what they read. A session's own row follows its own `turn.start` and `turn.complete` at once. Every value the panel and the line above the prompt read is written only when it changed (`sameData`): Claude draws every reader again on every write, equal or not.

**The leader.** One session per data folder does the work that's the same for all of them (`hooks/leader.ts`): the session `leader.json` names, while it rewrites it every pass and runs; else the lowest process id among the sessions Claude's registry has running whose heartbeat is fresh, of this format and process. It lists `claude agents --json --all` once a pass (that listing removes the registry file of a session that crashed, which nothing else does, and is checked against the files: what differs goes to the debug log), keeps the Remote Control pins (also as soon as a connection comes or goes in the registry), reopens what memory pressure closed, prunes old data, and runs `usage.py` after a turn ends somewhere (two minutes apart at least) and every 10 minutes, leaving the summary for the others. A leader that ends cleanly is replaced on its registry file's removal, within a second. One that crashed keeps its registry file, so it's replaced once its heartbeat is stale (45 s) or its record two passes old: the next one takes over at its pass and lists at once, which sweeps the dead one's file and its row. One that hangs is replaced the same way, and once it runs again it leaves the lead where it went while that record stays fresh (no back and forth). Two leaders for a moment do no harm: every duty is idempotent and under the lock it always had.

**The pass.** Every session reads everything again once a minute (`PASS_MS`, from an offset of up to 10 s of its own, so a machine's sessions don't read at once), whatever the events said: the registry and the service's jobs, the store's records, the leader's turn, `ccc`'s requests (one it finds that no event announced means the inbox isn't watched: it's read every 0.5 s from then on, as Claude won't watch it again in that process) and the queues other plugins fill, its own chores (a `/clear`'s new id, its agent, its usage and spend, the update in place) and the seen check's timer. A missed event (Claude didn't report a write, the Mac slept) costs a pass at most; after a sleep, the first pass waits for the session's own offset.

**Updating in place, and what's watched.** A reload (`/reload-plugins`, which the update in place runs) raises no new `SessionStart`, and Claude keeps watching what the module before it asked for. So `WATCH_SET` in `hooks/watch.ts` numbers the set of paths watched: `reloadDecision` never updates in place into an installed copy whose `watch.ts` has another number (the `↑` stays, and the debug log says why), and the module keeps what its `SessionStart` set up in `$.state` (`watching`), which a reload keeps too. A module that finds no `SessionStart` of its set behind it (a `/reload-plugins` you ran yourself across a change of the set, or a plugin ahead of it keeps `SessionStart` from it) starts its own watch of the same paths (`watcher.py watch-paths`), and until that's up, or while it's down, runs the short timer (requests every 0.5 s, the files every 3 s, the seen check every 2 s, chores every 15 s, the leader's turn every 20 s), with no `claude agents` call while the files can be read; a panel that came in by a reload and has neither says `Live updates off` until a start, `/clear` or compaction makes it live (unless this machine's starts find no `SessionStart` at all, the store's `startSkipped`: then nothing would, and it doesn't say `u`).

**What still runs on a timer, and why:**
- the heartbeat, every 15 s: the only way to know from outside that a session's mod runs (`!`, `ccc`'s offer to restart, notices, who can lead);
- the pass, once a minute: file events can be missed, and some changes have none (a crashed process);
- the leader's `claude agents`, once a pass: a crashed session's registry file, and the jobs the service stopped or removed, are known to the service only;
- the leader's reopen check, each pass while a pinned background session has no process: memory pressure has no event (`sysctl`, and the service's log read again only when it changed);
- the seen check, only while this session's answer is unseen and a window could show it: mods get no event when a terminal window comes to the front. Which windows are open and which one is in front are shared through the store, each stamped when its answer came back and marked while a session is asking, so the others don't ask too; with an agent view in front, the session that asks also reads its text once and shares the sessions it shows (their `⟨id⟩` tags): one question to Terminal (two with an agent view) every 2 s or so however many sessions are unseen;
- one timer for the next change of a row's time or `⧗`: time passes with no event;
- `claude --version` and `claude plugin list --json`, shared through the store, at most every 5 minutes: the installed versions, for `↑` and the update in place. While another session leads, only the leader runs them; a session about to run one says so in the store and the others use what's stored meanwhile, and one that fails keeps the answer before it and is tried again 5 minutes later;
- a restart another plugin queued (`$.sessions.restart`), every 2 s while it waits for the session to be idle;
- where nothing watches the session's paths (no `SessionStart` reached the mod), the short timer, only until the mod's own watch is up and while it's down;
- only while an action runs: an open New or Rename field, checked every 0.3 s (no event says Esc left it); Stop's 1.5 s pause before closing the stopped session's windows; "Restarted", once the window reattached (by process, since `session.attach` doesn't come for `claude attach`); and `ccc`'s short waits (an answer in `replies/` every 0.1 s for 3 s at most, a session it just created in `claude agents` every 0.3 s).

**Shared formats.** Every file in `~/.claude/mods/sessions-data/` and every notice between sessions carries `format=<n>`. A session or launcher that meets another format acts on nothing and says to restart the sessions (`u`, or `claude respawn <id>`); the panel marks sessions on another format with `!` and sends them nothing. There's no compatibility code for older versions: after an update, restart every session.

**ccc.** The setup installs `~/.claude/mods/sessions-data/bin/ccc`, which nothing rewrites afterwards. It runs the launcher (`hooks/visor.sh start`) of the copy of the plugin `claude plugin list --json` says is enabled, so it always matches the installed version (without an installed plugin, it uses the copy the setup ran from). That answer takes claude most of a second, so `ccc` keeps it per folder in `~/.claude/mods/sessions-data/lookup/` and asks again only once Claude's record of installed plugins (`~/.claude/plugins/installed_plugins.json`) or a settings file that can enable it (yours, the folder's or one above it, the managed one) is newer, or the copy it names is gone. Run `/sessions setup` again after an update to get a newer `ccc`. `hooks/launcher.py` decides what opens:
- the project root as the panel computes it (the nearest folder upwards with `AGENTS.md` or `CLAUDE.md`; a worktree under `<project>/.claude/worktrees/` walks from `<project>`), and its sessions, each in the project it started in (above: the heartbeats' roots, else the transcripts' first rows, else the folders Claude lists them in), for the pick, `ccc <name>`, `ccc tell`'s names, `ccc section` and `ccc tidy --here`;
- the order from `order/<root>`, which every panel of the project writes when its rows change (the unfocused order, the one rule in `state.ts`), or without a fresh one: waiting, working, idle, then by name;
- which windows show which session, from `ps` (a `claude attach <id>` per terminal);
- what to bring forward or open, as in the table above.

To bring a window forward it writes a request to a running session's `inbox/<sessionId>`; that session's mod reads it on the file's event (about 0.6 s later; every 0.5 s on the short timer), brings the window forward with the platform code (`hooks/platform/`) and answers in `replies/`; `ccc` waits 3 s for that answer, and a request read after that is dropped unanswered. Before opening a session, `ccc` writes a focus request in its inbox: the panel takes the keyboard then, even before the viewer attaches (it holds when the window attaches). If `claude attach` fails within 3 s of the first open, `ccc` picks again once without that session, unless the panel wrote a switch for the window meanwhile.

**Switching in one window.** Every window opened with `ccc` (or by the panel) runs the launcher (`hooks/visor.sh`), which opens `claude attach <id>`, and beside it the window's watcher (`hooks/launcher.py watch`, one Python process per window). As each viewer starts, the launcher writes what the window shows to `~/.claude/mods/sessions-data/windows/<tty>.showing` (its terminal, the session, and the viewer's, launcher's and watcher's processes). On Enter the panel reads those files, with no command: if exactly one window shows its session, it writes the next session to that window's file (`windows/<tty>`) with `end=1` as the last line, and the watcher sends the viewer a SIGHUP at once; if a window shows the target, the panel brings that one forward instead. Right after writing, the panel checks with one `ps -p` that the window's launcher and watcher still run there (on that terminal, those programs); a `.showing` that a launcher left behind (killed, its watcher stopped, the computer restarted) fails it, both files go, and the switch goes the usual way. The usual way, which also serves an open agent view, a session shown in several windows, and a session that the last windows listing shows in a window that says nothing (a `claude attach` typed by hand): one `ps -A` finds the windows, on macOS Terminal says which one is in front, and the panel writes the window's file and closes the viewer with `kill -HUP`. Either way the launcher opens the next viewer over the last frame, on the alternate screen, with echo off and no line from bash, so the window goes from one session's frame to the next one's. What's typed during a switch by the launcher windows is dropped: once the watcher has ended the viewer, it flushes the terminal's input every 2 ms while the terminal is in the launcher's mode between viewers (canonical, no echo, Enter no line end) and stops as soon as the next viewer takes it (raw), 2 s at most; a switch the usual way drops nothing. Measured in hidden terminals (Haiku, 230×45, median of 16 switches, portable code path, two runs each): from Enter to the target's panel, 0.135–0.143 s for a short session and 0.134–0.137 s for one of 400 turns, against 0.176–0.192 s and 0.183 s the usual way; most of what's left is `claude attach` starting (about 0.1 s). The session you leave spends about the same CPU on a switch either way (0.08 s), since `ps` runs as a process of its own. On a Mac the usual way also asks Terminal which window is in front (31 ms or more), which a switch from a window opened with `ccc` no longer does. Nothing is typed into the terminal. A window without the launcher can't be switched in place: the panel opens the session in a new window next to it. `claude respawn`'s reopen (`u`, `$.sessions.restart`) writes the window's file with no `end`: the restart ends the viewer, and the launcher reopens it.

**Focus on arrival.** After a switch from a row of the panel (Enter or a click), the origin session sends the target a notice with `$.session.send`. The target's mod intercepts it in `session.receive` by returning `{ consumed }`, so it never reaches the model, and marks what it answered seen; if you switched with the keyboard (`focus`), it also gives its panel the keyboard, and if you clicked the row (`seen`), the keyboard stays where it is. Stop and Restart questions work the same way: the origin asks "ask there", the target asks, sends the window back and the answer, and the origin does what was chosen. When the target's dialog can't show (`$.ui.ask` rejects without the person's dismissal: no AskUserQuestion in its tools), the answer says so (`unshown`) and the origin asks in its own window. The ask carries the origin's id, title and kind, so the target finds it even when its own panel doesn't show it (the `f` filter, another project root). Claude sends a notice only from a session whose agent has the SendMessage tool (`$.session.send` answers not delivered otherwise): a target without it leaves the answer in the store (`answer:<origin's id>`) and rings `bell/answer-<origin's id>`, and the origin's panel reads it then; an origin without it asks in its own window from the start. Notices only go to sessions whose heartbeat shows they run the same format, so a session whose mod doesn't run never gets one as text.

**Restart.** `claude respawn <id>`: the same session (id, name, conversation) in a new process that reloads MCP servers, plugins and settings, on the installed version. The installed version comes from `claude --version` (every 5 minutes, shared), each session's from `$.session.version()`. To restart its own session, `claude respawn` can't run as that session's child: the service closes the session and takes the command with it before restarting it (it ends up stopped). So it runs detached, in its own process session (`perl -MPOSIX`, `fork` + `setsid`), after each window's launcher is told to reopen the session. If the session is still alive 15 s later, the restart failed: the notes are removed and you're told. "Restarted" is announced by the new process once it sees, by process, that the window reattached (`session.attach` doesn't fire for `claude attach`).

**Rename.** There's no command to rename another session. A mod can run a Claude command in its own session as if you typed it: `$.command.run({ command: 'rename', args })`. For another session, the origin's mod sends a notice with `$.session.send` and the target's mod runs its own `/rename`. A session whose panel isn't running (or runs another version) doesn't get the notice; the panel tells you to use `/rename` there.

**Pinning with Remote Control.** There's no command to pin: Ctrl+T in `claude agents` just writes `~/.claude/jobs/pins.json`, a list of ids, which the background service reads every time it decides whether to close a session. The mod does the same: it takes the same lock as Claude (the `pins.json.lock` folder), writes the list to a separate file and moves it into place. Whether a session has Remote Control is in its `~/.claude/jobs/<id>/state.json`: Claude writes `bridgeSessionId` when it's turned on, keeps it across relaunches and removes it when it's turned off. The leader checks for all of them once a pass and whenever a Remote Control connection comes or goes in the registry; which sessions the mod pinned is kept in the shared store (`autoPins`). When that record is missing (a new store, or a lost one), the mod rebuilds it once, under the same lock: every pinned session with Remote Control on counts as pinned by the mod, so a session you pinned by hand that has Remote Control on is then unpinned when its Remote Control goes off. A session another plugin keeps pinned (`$.sessions.pin`, recorded as `pluginPins`) stays pinned when its Remote Control goes off, and a plugin unpins only the pins its calls added. A pinned session you stop doesn't come back on its own: the service only relaunches running ones.

**Reopening after a memory shortage.** Why a session closed comes from the background service's log (`~/.claude/daemon.log`): a session counts if the last thing that happened to it is `retire <id>: … [low memory…]` and it didn't start again afterwards (`claimed-spare`/`spawned`). Memory is read with `sysctl kern.memorystatus_vm_pressure_level` on macOS (1 normal, 2 warning, 4 critical: the same figure the service uses to close sessions). It reopens with `claude respawn <id>`. To test it without running out of memory, `SESSIONS_DAEMON_LOG` (in the `env` of a test session's `--settings`) points the mod at another log file, with a closing line added by hand.

**Sessions that ended with the background service.** A service that goes down with its workers leaves no line for each session in its log: its next start says how many it found dead (`bg adopt: … dead=3`), and that's the time the panel's line gives. A stopped background session counts when nothing of its own came after it last ran (no `retire`, no `settled`: `settled <id> (killed)` is a claude stop, `(done)` or `(crashed)` an end of its own), you didn't stop it from a panel (`personStop`), and that death came at or after its last run (its last `claimed-spare`/`spawned`, or its mod's last heartbeat); with no sign of when it last ran, it doesn't count. Each panel works it out from what it already reads: the list, the log (read again only when it changed) and the heartbeats, at each refresh and whenever a session comes or goes in any folder, with no command or timer of its own. `b` respawns them through the same path as `u`; the dismissal is the store's `endedDismissed` (that death's time), and `broughtBack`, taken under `<data>/bringback.lock`, keeps two panels from respawning the same session. `ccc tidy` reads the same log (`SESSIONS_DAEMON_LOG` points it elsewhere too) and the heartbeats, but not the store, so it can't see a stop from a panel whose line the log no longer has: there it's a mark, nothing is done with it. To try it without taking the service down, point a test session's `SESSIONS_DAEMON_LOG` at a log of its own with an `adopt: … dead=N` line written after its sessions last ran.

**Token usage.** `hooks/usage.py` reads `~/.claude/projects/**/*.jsonl`. Each model response carries `message.usage`:
- `input_tokens`: uncached input, a few tokens per response;
- `cache_read_input_tokens`: the conversation Claude rereads from the cache;
- `cache_creation_input_tokens`: what's new at each step, written to the cache;
- `output_tokens`: the output, thinking included (`output_tokens_details.thinking_tokens`).

The same response appears several times in a file (once per content block), and sometimes copied into another file when a session is resumed, so it's counted once, by `message.id:requestId`, like [ccusage](https://ccusage.com). Each response counts in the project its session belongs to, whatever folder it was working in: the root in its heartbeat (`alive/<sessionId>`), else its transcript's first `cwd` (a subagent's file, `<sessionId>/subagents/`, goes by its session's), else the row's own `cwd`; `p`'s project view shows what the project's sessions spent. It reads only what's new in each file since last time and keeps totals per day (35) and per hour (48), in `~/.claude/mods/sessions-data/usage/` (rewritten only when a run found something new), with what it answered last in `~/.claude/mods/sessions-data/usage/summary.json`: a session that finds that from the last minute uses it instead of running `usage.py` again. The first run takes a few seconds; afterwards, hundredths. Several sessions can run it at once: it takes a lock.

**Status line.** `statusline/statusline.sh` reads the status JSON Claude passes on stdin and prints model · effort · folder (and the working folder when it drifted) · git branch · context % (yellow from 60 %, red from 80 %) · cost and lines changed. The setup copies it to `~/.claude/mods/sessions-data/bin/`, which is what it points `statusLine` at.

## Old pre-started sessions

Claude's background service keeps a pre-started Claude process ready (a "spare") and hands it to the next session that starts: `claude --bg`, a new session in the agent view, the agent view's own hidden pre-started session, `claude respawn`. A spare runs none of a mod's code until it's claimed, and the claim checks no age: one started hours earlier, before a plugin update, can come up running no mod at all (no panel, no heartbeat, no `/sessions`). There's no setting to turn spares off. So:

- the mod starts from its first draw, prompt or notice when `session.start` didn't come;
- its heartbeat shows from outside whether it runs: the other panels mark the row with `!`, and `ccc` offers to restart the session before opening it (`u` does the same from a panel); `/sessions status` inside a session says how its mod started;
- a restart (`claude respawn`) starts a new process; right after a claim the next spare is seconds old, so a session `ccc` just created gets one automatic restart if its panel doesn't come up.

## Lessons (API pitfalls)

- **A pane's focus follows positions, not elements.** If rows reorder while the pane has the keyboard, the highlight lands on another row. So while the pane is focused, rows keep their places.
- **A field that appears with `autoFocus` doesn't take the focus if the pane already had the keyboard.** The focus stays on whatever is now at that position: with the field above the rows, what you typed went to another row (and a space opened it), and when the field closed the focus fell on `d: Day` with the arrows stuck. So the fields go below the rows, the mod moves the focus to them with `$.ui.focus`, and the arrows bring a stray focus back to the selected session.
- **`$.ui.focus({ requestId, key })`** only works with the pane already focused, can answer "the focus moved meanwhile" (retry), and doesn't fire the mod's own `ui.focus` hook.
- **`$.ui.ask`** is the AskUserQuestion dialog: up to 4 options, it adds "Type something" and "Chat about this", and it queues behind a pending permission prompt. So the panel doesn't ask in a session that's already waiting for you.
- **The panel's colors can lag**: about 0.6 s behind Claude's files, a pass when an event was missed. Before something that cuts work short, the status is checked right then.
- **`claude respawn`** cuts a running turn and closes that session's viewers. Artifact watches (`artifact_watch`) aren't work: Claude carries them over to the new process. To count background tasks, do what Claude does: `inFlight.tasks - inFlight.drainableMonitors`, from the background service's state.
- **`claude respawn` of your own session from a child process leaves it stopped**: run it detached (`setsid`).
- **A background session's process has a terminal too** (the background service's internal one): when looking for the window showing a session by its processes, only a regular session's own terminal counts.
- **`session.attach` doesn't fire for `claude attach`** clients (only for remote surfaces like the phone, desktop or VS Code).
- **An Input's `value` isn't replaced by typing**: what you type is appended to it.
- **`$.process.run` rejects** if the command doesn't exist or times out. Every call goes through `runSafe`, which turns that into an error code.
- **A session can change folder, and the folder it left can be deleted**: EnterWorktree and ExitWorktree (and `/cd`) move it, a session restarted in a worktree starts there, and the worktree can be removed afterwards. A command left to run in that folder can't start (every command failed: "Couldn't read the session list"). So every command the mod runs gets a folder that exists (the home folder; the project root only for `claude --bg`, checked first). The project stays the one the session started in, recorded at its first start (`$.session.root()` then, or its transcript's first row), not the folder it's in now: following the folder took a session that entered a worktree outside its project out of every panel of the project, and its own panel onto the worktree. `$.fs.ancestors` walks from where the session started, so the `AGENTS.md`/`CLAUDE.md` markers are looked for on disk.
- **A `cd` in a shell command doesn't move a session** (checked on Claude 2.1.319, into a subfolder and into an `--add-dir` folder, through a restart): its registry file, its background job's `cwd` and `claude agents` keep the folder it was in; only `$.session.cwd()` and the `cwd` of the transcript rows written after it follow the shell. `/cd` (which you type) and the worktree tools do move it: `$.session.root()`, its registry file and `claude agents` say the new folder, and its transcript moves to the new folder's `~/.claude/projects/` folder with a `relocated` row, its first row still in the folder it started in. So a transcript is found by the session's id, not by its folder's name. The background job's own record differs by tool: after `/cd` its `cwd` and `originCwd` (which, despite its name, is the new folder) say the new folder; after EnterWorktree with a path (2.1.319) its `cwd` stays where the session was, and `originCwd` appears only at ExitWorktree (the folder it went back to).
- **EnterWorktree with a path outside `<project>/.claude/worktrees/` asks first**: a permission prompt (a "permission-root relocation" for "a model-supplied worktree outside .claude/worktrees/"), so a background session nobody is viewing waits there (red, waiting for you) until you answer it in its window. On 2.1.319 it refuses a worktree of another repository; `/cd` takes a session anywhere.
- **The validator** wants the state types (`PluginState`) in `types/index.d.ts`, with no `import`.
- **A `ui.render` hook's own `$` can start the mod**: from a timer it schedules (`$.clock.after(0, …)`, since a draw only draws), it can read the session's id, write the store and files, start more timers, open the panel and register commands. The line above the prompt is drawn even in a background session with no window attached, sometimes before `session.start`.
- **Focus taken with no window attached holds**: `$.ui.open({ focus: true })` in a background session nobody is viewing gives the panel the keyboard, and it still has it when `claude attach` connects.
- **A panel opened unasked at the pre-started process's 200 columns stays placed** when a narrower window attaches.
- **`claude --bg` refuses folders Claude never trusted** ("Workspace not trusted…", exit 1) and your home folder; a subfolder of a trusted folder is trusted, unless it's a git repository of its own. Trust is checked at each start, so `claude respawn` refuses too once the folder became a repository after the session started (checked on 2.1.319), and the session keeps running. `--debug-file` works with `--bg` (in a claimed pre-started process too), and `claude respawn` keeps it.
- **The agent view draws no panes**: a mod's panel shows only in a session's own screen.
- **A mod can run `/reload-plugins` itself** (`$.command.run({ command: 'reload-plugins' })`, checked in a test session). With unchanged code nothing reloads; with new code the old module's timers stop, the new module's `register` and `session.start` run, and its panel comes back. Not checked here: that it picks up a version `claude plugin update` installed from a git marketplace (the docs say `/reload-plugins` re-reads the installed copy), and whether a version that adds permissions or MCP servers makes the reload ask first.
- **What Claude watches for a hooks module is set at `SessionStart` only** (`watchPaths`, after the paths of the plugins beneath), and a reload keeps it: a module that came in by a reload watches what the one before it asked for, until the next start, `/clear`, compaction or resume. A path can be missing when it's asked for only if it's the one missing name in a folder that exists: Claude then waits on that folder for it, and of several names missing in one folder it ever watches one (the others never, even once made), and none whose folder is missing too. A single file removed and made again isn't watched any more, and a `/clear` or compaction that hands the same list watches nothing anew: a path missed stays missed until the session restarts. Claude says a change or a new file about 0.6 s after it (it waits for the size to hold for 0.5 s, so a burst of writes is one event) and a removal after about 0.15 s, in a background session with no viewer too, and the event goes to every plugin's hook. Watching `$.store`'s file is no use: reading it touches it.
- **Every `$.state` write that lands draws its readers again, equal or not**, and what's drawn again is the whole component (the panel), not the part that read the value: splitting a value into smaller ones gains nothing, writing less does. So every write is compared first (`sameData`), and a row's time is written only when its label changes.
- **A hooks module can't hand `$` to a function of another module** (the engine refuses to load it: "$ itself is passed as an argument"). So the reads, writes, timers and hooks stay in `register.tsx`, and `watch.ts`, `leader.ts` and `state.ts` hold logic with no I/O of its own, which the tests call directly.
- **`$.store` is no bus between sessions**: every read parses the whole file and touches it, every write rewrites it whole under a lock, and nothing says it changed. What sessions share and change often goes with a bell file that the others watch.
- **A crashed session keeps its registry file** until a `claude agents` listing (which checks each process) removes it; the background service removes its own sessions' at once. A mod can't tell a process is gone without running a command.
- **`/clear` changes `$.session.id()`** (the transcript's id) but not the short id of `claude agents` and `claude attach`; `session.end` comes with `reason: 'clear'` and no `session.start` follows, and the module, its timers and its panel stay. So a session's short id comes from the official list, never from the start of its session id (that was wrong after a `/clear`, and its window wasn't found).
- **A session's agent is in its transcript, not always at the top.** A session started with `-n <name> --agent <agent>` opens its transcript with `custom-title` and `agent-name` rows, then `agent-setting`; `/clear` starts a transcript without it, and a restart appends one after the messages.
- **The `$` built in `engine.create` can't be handed to a function** (the validator refuses it), and `$.env.get` takes a variable's name written out: a noun's methods reach `$` through closures over it. A method's calls run inside the calling plugin's hook.
- **The line above the prompt is shared**: a mod that answers its `ui.render` without `await next(e)` hides what Claude and other mods draw there. In `claude plugin test` nothing draws it beneath the mods: the test answers that `ui.render` itself.
- **The agent view's hidden pre-started session isn't in `claude agents --json`**: a cleanup of the data of sessions missing from the list must spare sessions with a fresh heartbeat.
- **A tool a mod registers for the model never prompts** (checked on 2.1.319): a `tool.call` hook that answers without `next` skips the engine's permission step, so an `ask` rule for the tool is silently bypassed and no classifier runs. A `deny` rule still takes the tool away. `$.tool.check({ tool, input })` tells the hook about an explicit rule (`{ decision: 'ask', rule }`; with no rule, `{ decision: 'ask', reason }` in default mode), so the mod refuses in place of the question. `$.tool.check` itself runs no classifier and no model request (checked in auto mode: no request between the call and its answer, the check in about a millisecond).
- **An unlisted tool holds an agent session's start 8 s** (2.1.319): `$.tool.register` waits for the tool to show in the session's tools, and an agent whose `tools:` line doesn't name it never shows it; on every start and restart, `$.tool.register` resolves only after 8 s (debug: `not yet in the session's tools after 8000ms`). Not awaited at `session.start`, a tool never shows in an agent session at all (in a plain one, from a later request). So the registration is awaited for a moment only, and skipped where the agent's file leaves the tool out.
- **`classic.SessionStart` is raised beside `session.start`, not inside it** (2.1.319): it can settle after `session.start`'s whole chain, so a `session.start` hook that needs what it carries (`agent_type`) waits for it.
- **A plugin ahead of yours can keep a classic event from it, and only a managed one does it visibly** (2.1.319): `next.to` (continue beneath the user tier) is for managed plugins only: a user plugin's module that calls it doesn't load ("next.to is available to managed plugins (prependPlugins / appendPlugins) only"). A managed or built-in plugin that sends `SessionStart` on past the plugins you installed makes Claude say, at each start, that their hook "was skipped"; a user plugin that stands before another (one that lists it under `dependencies`) can keep an event from it only by answering without `next`, which only the debug log says. The skipped hook never runs, so it can't learn who skipped it: `next.trace`'s `bypassed by <plugin>` is for the hooks above, and `plugin.register` judges only the plugins admitted after the one judging. What only `SessionStart` gives has to come from elsewhere: no other hook result and no `$` call has Claude watch a file (`watchPaths` is `SessionStart`'s alone), and the agent a session runs as is in Claude's registry of running sessions (`~/.claude/sessions/<pid>.json`'s `agent`, there before `session.start`, absent with none; interactive and background) and in a background job's `respawnFlags` (`--agent <name>`).
- **Hooks of plugins that depend on another stand before its own** (2.1.319, debug: `hooks module order: dependencies register …`): a plugin that lists `sessions` under `dependencies` hears a `mcp__sessions__wake` call before `sessions` answers it, and can refuse it; one that doesn't (whatever its name) stands after, and never hears it. Every plugin's `tool.check` hook hears a `$.tool.check`, whatever the order.
- **SendMessage to a stopped session fails at once** ("No agent named … is reachable"): it isn't kept for it, and doesn't wake it. ListAgents lists only running sessions, of every folder, by Claude's name for each and a `[ref]` that's per process: it changes at each restart, and isn't the short id. A `$.tool.call` of ListAgents from inside a `tool.call` hook puts no row in the conversation (the transcript gets a `tools-used` row only).
- **A mod can watch files itself where Claude won't** (2.1.319): `$.process.spawn` streams a child's output for as long as the loop that reads it runs (leaving the loop, the module unloading or the session's end kills the child; a hook's return doesn't), so a child that sleeps in the kernel's file watch costs nothing until a file changes. kqueue needs a descriptor per file (a folder's only says entries came or went, and a file renamed over another is a new one to watch), inotify a watch per folder and an instance per process (`fs.inotify.max_user_instances`, 128 on many systems), and a folder made between a look and its watch needs one more look. An async generator queues a `return()` behind the `next()` it's waiting on, so the mod ends its watcher by the process id it printed, which needs nothing from the child. In `claude plugin test`, a stand-in for `process.spawn` is an `async function*` that yields `{ stream, text }` and returns `{ value: { code, signal } }`.
- **`$.fs.write` makes the file first and writes its bytes after**: another process watching the folder sees the new file empty, and a write over a file that's there doesn't change the folder at all. So the window's watcher (kqueue on macOS) also watches the file itself while it's there, and reads a file as whole only by its last line (`end=1`); inotify on Linux tells every write of every file in the folder.
- **bash 3.2 (macOS's) reports a viewer killed by a signal** ("Hangup: 1 …", written over the last frame) whether it ran in the foreground or as a background job, and a background job ignores SIGINT and SIGQUIT with no way to give them back (`trap -` in it doesn't). So the launcher runs the viewer in the foreground inside `{ (…); } 3>&2 2>/dev/null`, the viewer's own stderr on fd 3; bash 3.2 has no `BASHPID` either, so the viewer's pid comes from `/bin/sh`'s `$$` just before it execs it.
- **`claude attach` starts about 10 ms slower when nothing ran just before it** (checked on 2.1.319 on an Apple Silicon Mac): the usual way runs a `ps -A` of 60 ms just before the viewer starts, and the viewer then takes about 92 ms to its first byte; with no `ps` first it takes about 103 ms (and 0.015 s more CPU), with a dummy `ps -A` first about 95. Leaving the alternate screen or not, echo, and starting it in the background change nothing, and the research's prototype found starting it 60 ms later doesn't help either: most likely the CPU's own pace after a quiet moment, not the launcher.
- **Keys typed while `claude attach` starts go to the session's prompt box, not to a pane that has the keyboard** (2.1.319, keys sent 60 ms after Enter): kept by the terminal, a letter reached the target's prompt box in 5 of 8 tries where that box had the keyboard on arrival (0 of 8 where the panel took it at once), and with it there the panel no longer had the keyboard; such letters, sent later by an Enter, became messages. Dropped, none did (0 of 16), and a second Enter never sent a draft waiting there nor hopped again (0 of 8). The viewer reads its input from its start, but takes the terminal (raw) only about 0.1 s in, right before its first byte (+0.11 to +0.14 s from Enter, the launcher's own mode from +0.01 to +0.03 s): in a canonical mode a letter waits as part of a line, while an Enter (CR, read as a line end) is a whole line it reads at once. So the launcher's mode between viewers keeps Enter from ending a line (`-icrnl`), and the window's watcher flushes the terminal's input while it's in that mode; a drop once, before the viewer starts, would miss what's typed while it starts. With 0.16.0's launcher the terminal echoed such keys over a blank screen and they were lost.
- **A panel's redraw doesn't reach its window before that window's viewer ends** when the switch is quick: a mark drawn on Enter (an arrow on the target's row) never showed in 8 of 8 switches (the viewer ends about 20 ms after the key), and showed instead for 0.2 s when the window came back to that session, which first draws the frame it had. Feedback in the session you leave would need the switch to wait for it.
- **A mod can send PushNotification itself**: `$.tool.call({ tool: 'PushNotification', message, status: 'proactive' })` from the mod's own timer needs no permission and opens no dialog (checked with no viewer attached, and with a question pending), answers in a few ms with `pushSent`, `localSent` and `disabledReason` (`user_present` while you're at the computer: "this terminal is active"), and puts no row in the conversation, so the model never sees it (the transcript gets a `tools-used` row only, and the tool isn't loaded for the model). Not checked here: that it reaches the phone with Remote Control on. `$.ui.notify` in a background session answered `no-channel` in a terminal that has no notifications, with or without a viewer attached.
