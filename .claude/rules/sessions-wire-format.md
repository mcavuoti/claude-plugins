# sessions: shared formats carry a version, and nothing keeps old ones alive

Several sessions run the `sessions` mod at once and talk through shared data: the store, the files in the data folder, the notices between sessions, and the launcher. After an update the owner restarts every session, so there is no compatibility code for older versions of the mod. Instead, version skew must be harmless and visible:

- **Files and notices carry `format`.** `FORMAT` in `hooks/state.ts` (and the same constant in `hooks/launcher.py`, `hooks/visor.sh`, `hooks/usage.py` and `setup/ccc`) is the format of the heartbeats (`alive/`), the order file (`order/`), the inbox requests (`inbox/`), the launcher's window files (`windows/`: what a window opens next, and `<tty>.showing`, what it shows), the mirrored settings (`config`), `ccc tell`'s requests, status files and opt-in (`tell/`), `usage.py`'s output, summary (`<data>/usage/summary.json`) and cache, `ccc`'s plugin lookup per folder (`lookup/`), the bells (`bell/`: they say what to read again, never the data; `hooks/watch.ts`), the leader's record (`leader.json`, `hooks/leader.ts`), and the notices (`sessions-notice:7f3a` + JSON with `format` and `kind`). Change any of their keys or meanings → raise the format in all of those places in the same commit. A new notice kind doesn't: every receiver consumes a kind it doesn't know and does nothing with it, so a session on an older version only misses what the new kind does.
- **A reader that meets another format does nothing harmful and says so:** it doesn't act on the data, consumes a notice so it never reaches the model, and tells the person to restart sessions (`u`, or `claude respawn <id>`). Senders only send notices to sessions whose heartbeat shows the same format.
- **Person data has its own version.** What the person chose and keeps for good, such as `sections.json` (`sectionsFormat`, `SECTIONS_FORMAT` in `hooks/state.ts`), isn't wire data: it doesn't follow `FORMAT`, changes only by adding fields, and a write keeps the fields it doesn't know. It's never silently ignored: a reader that meets a newer version leaves the file untouched and says so (restart, `u`). A breaking change would ship a one-time rewrite into a new key or file in the same commit, never code that reads two shapes.
- **Store keys are English.** When a stored value changes meaning, give it a new key name rather than reading two shapes.
- **Locations are overridable** for tests: `SESSIONS_DATA_DIR` (the mod's files), `SESSIONS_JOBS_DIR` and `SESSIONS_DAEMON_LOG` (Claude's background service), `SESSIONS_REGISTRY_DIR` (Claude's registry of running sessions, read only), `SESSIONS_CLAUDE` (the claude command), `SESSIONS_PLUGIN_VERSION`/`SESSIONS_PLUGIN_SINCE` (the installed plugin). A new location gets an override too, so test sessions never touch the owner's files. A session with a location override set (`SESSIONS_DATA_DIR`, `SESSIONS_JOBS_DIR`, `SESSIONS_DAEMON_LOG`, `SESSIONS_CLAUDE`) is a test session and keeps all its store keys under a namespace of its own (`storeNamespace` in `hooks/state.ts`): every store access goes through `storeGet`/`storeSet`/`storeDelete`/`storeKeys` (a new override joins the list there and in `storeNamespaceOf`). `SESSIONS_PLUGIN_VERSION`/`SESSIONS_PLUGIN_SINCE` count only beside a location override: ccc sets them for its launcher, so alone they make no namespace and don't stand in for the installed plugin. No claude command the launcher, `visor.sh` or the mod runs gets them (launcher.py's `CHILD_ENV`, visor.sh's subshells, the mod's `runSafe` blanks them).
- **Nothing a running session does rewrites what other sessions or the shell run.** The `ccc` command and the status line copy are installed by the setup (`~/.claude/mods/sessions-data/bin/`); `ccc` finds the enabled plugin each time it runs.
- **What the engine watches is a set with its own version** (`WATCH_SET` in `hooks/watch.ts`): `classic.SessionStart` hands it the paths, and a reload keeps them and raises no SessionStart. A version that watches a new kind of path raises `WATCH_SET`, and an update in place never crosses it (`reloadDecision`); a module that finds no SessionStart of its set in the session (the `watching` state) watches the same paths itself (`launcher.py watch-paths`, with the kernel watch the platform names, `fileWatch`; a SessionStart ends it), reads on a short timer only until that's up and while it's down, and says why: after an update in place, that a restart (`u`) or `/clear` makes it live; where a plugin ahead of it keeps SessionStart from it (a fresh start with none, or the store's `startSkipped`), that a restart won't, and it takes the agent from Claude's registry or the job's flags instead (`roleFromFiles`).

The keys, files and fields are listed where they're defined: the comment above `storeGet` in `register.tsx`, and `state.ts` (Heartbeat, orderFileText, InboxRequest, WindowTarget, Showing, TELL_MAX_BYTES, buildNotice, MarkSlot, SECTIONS_FORMAT). The API other plugins call (`$.sessions`) has its own rule: `.claude/rules/plugin-contract.md`.
